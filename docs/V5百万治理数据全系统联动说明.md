# V5 百万治理数据全系统联动说明

## 1. 本次修改目标

V5 在 V4“百万 JD 连续治理”基础上，将已经完成治理的 `zhitu_governed_job` 与 `zhitu_governed_job_skill` 正式升级为岗位市场分析主数据源，并完成以下四组修改：

1. JD 解析页的“最近治理结果抽样”和“系统内即时解析记录”增加独立滚动容器，避免百万数据抽样把页面无限拉长。
2. 总览、数据治理、岗位探新、年度验证、能力演化、能力图谱全部切换/联动百万治理数据，不再以 120 条 H2 演示 JD 作为岗位市场分析主数据。
3. 总览“完整业务闭环”前移至技术栈分布之前，01~06 全部可点击跳转。
4. 新岗位候选定义补齐赛题要求的五项字段：岗位名称、核心职责、必备技能、加分技能、典型行业应用场景。

## 2. 数据源关系

```text
career_data_governance.dataset_job_raw
        │
        │ 原始百万 JD（只读）
        ▼
zhitu_temporal_holdout
        │ 2026 固定 1000 条最终测试数据
        │
        └── 其余训练池
                ▼
        zhitu_governed_job
        zhitu_governed_job_skill
                │
       ┌────────┼────────┬────────┬────────┬────────┐
       ▼        ▼        ▼        ▼        ▼        ▼
      总览      数据      探新      验证      演化      图谱
```

H2 继续保留人工审核、智能体运行记录、人岗匹配、学习路径等业务状态。其中 `emerging_candidate` 和 `evolution_event` 作为“从百万治理数据计算后物化的审核结果表”，并非再从 120 条演示 JD 推导。

## 3. 各页面现在读取什么数据

### 总览 `/`

直接从 MySQL 治理表统计：

- 已治理岗位数量
- 有效分析岗位数量
- 标准岗位数
- 技能证据关系数
- 技术栈岗位分布
- 年度岗位数量
- 高频技能证据
- 数据可信度 / 重复情况

候选新岗位数量、审核数、匹配报告等业务状态继续从 H2 读取。

### 数据 `/governance`

主区域直接展示百万治理结果：原始总量、治理完成量、有效分析量、重复模板、低质量、质量均值、治理结果抽样。

原来的 CSV / 文档 / 网页导入入口继续保留，作为“新增补充数据源”，但不再代表百万历史训练数据。

### 解析 `/parsing`

继续作为百万 JD 治理与结构化解析控制台。V5 增加两个滚动区域：

- 最近治理结果抽样：最大高度约 430px，表头吸顶，可纵向/横向滚动。
- 系统内即时解析记录：最大高度约 360px，表头吸顶，可纵向/横向滚动。

### 探新 `/emerging`

后端从治理后的最新年份和上一年份进行岗位级聚合，重复模板不重复计票，并生成：

- 岗位名称
- 核心职责
- 必备技能
- 加分技能
- 典型行业应用场景
- 新颖度
- 增长强度
- 可信度
- 幻觉风险
- 样本数 / 来源数

候选结果同步写入 H2 `emerging_candidate`，因此可信审核中心无需改表即可继续审核。

### 验证 `/forecast`

年度训练数量现在明确显示：

- 原始总量
- 原始训练池
- 已治理数量
- 有效训练数量
- 测试数量

真正进入年度实验的是 `valid_for_analysis=1` 的治理后训练数据；2026 最终验证仍只使用固定 1000 条 Holdout。

### 演化 `/evolution`

直接比较治理数据最近两个有效年份的岗位技能证据，输出：

- `ADDED` 新增能力
- `WEAKENED` 弱化能力
- `MODIFIED` 要求变化

结果同步物化到 H2 `evolution_event`，兼容人工审核和智能体问答。

### 图谱 `/graph`

岗位节点与技能边全部从百万治理数据动态生成。边权综合：

- 去重后岗位证据
- `duplicate_weight`
- 技能抽取 `confidence`
- 必备/加分要求类型

按技术栈和级别筛选仍然有效。

## 4. 总览 01~06 跳转

| 编号 | 模块 | 路由 |

整张步骤卡可点击，而不是只有标题文字。

## 5. 新岗位五类定义是如何生成的

### 岗位名称

从当前年度治理岗位 `title_standard` 聚合，经岗位名称标准化后进行年度增长与新颖度计算。

### 核心职责

从该候选岗位高质量 `description_clean` 中筛选职责句（负责、设计、开发、构建、部署、优化、落地等），按跨 JD 支持频率排序，最多展示 4 条。证据不足时才使用技术栈通用职责兜底。

### 必备技能

优先读取 `zhitu_governed_job_skill.requirement_type='REQUIRED'`，按去重权重 × 技能置信度的证据强度排序。

### 加分技能

优先读取 `requirement_type='BONUS'`，并主动排除已进入必备技能集合的技能，避免前端重复展示。

### 典型行业应用场景

优先使用该岗位在当前年度真实 JD 中的行业分布，再结合技术栈形成“行业 · 场景”描述；当行业字段证据不足时使用技术栈场景兜底。

## 6. 覆盖方式

V5 补丁保持原项目目录结构。关闭前后端后，将补丁内容复制到项目根目录并选择“替换目标中的文件”。

不增加新的 npm 依赖，因此无需删除 `node_modules`，通常也无需重新 `npm install`。

覆盖后：

```powershell
# frontend
npm run type-check
npm run dev
```

后端在 IDEA 中重新启动 `ZhituApplication`。

## 7. 已经治理完百万数据后要不要重新治理

不需要。

只要页面 `/parsing` 仍显示：

- 治理完成率 100%
- `readyForAnalysis = true`
- 2026 Holdout = 1000

V5 会直接复用现有 `zhitu_governed_job` 与 `zhitu_governed_job_skill`。

建议覆盖后执行一次：

1. 总览刷新。
2. 探新点击“重新扫描百万岗位”。
3. 演化点击“执行演化分析”。
4. 图谱刷新。
5. 验证页检查各年份“有效训练”数量后再运行回测。

其中第 2、3 步用于把 V5 的百万数据计算结果重新物化到 H2 审核表。
