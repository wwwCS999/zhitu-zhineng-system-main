# V6 年度动态探新与数据解析合并说明

## 1. 年度动态探新

探新页面新增目标年份下拉列表。例如选择 2025：

- 输入：2024 年全部已治理、允许分析的 JD；
- 候选生成：只使用 2024 年岗位的后半年动量、样本支持、企业覆盖、多来源支持、质量分以及技能证据；
- 输出：预测 2025 年高潜候选岗位；
- 禁止：使用 2025 年真实 JD 参与候选排序；
- 验证：2025 年真实 JD 只在“年度验证”页面参与 Precision / Recall / F1 / Trust 回测。

因此不存在“拿目标年份真实数据反推目标年份候选”的未来数据泄漏。

## 2. 数据与解析页面合并

原“数据治理”导航已并入 `/parsing`：

1. 新增岗位 CSV；
2. 行业报告 / 岗位标准文件；
3. 公开网页；
4. 百万历史 JD 连续治理；
5. 最近治理结果人工修订；
6. 新增 / 系统内 JD 即时解析。

原 `/governance` 地址自动重定向到 `/parsing`。

## 3. 治理后 JD 人工修改

“最近治理结果抽样”每行新增：

- 修改：岗位名称、企业、城市、年份、技术栈、岗位级别、职位描述、分析准入；
- 能力项：添加技能、删除技能，并区分必备 / 加分 / 一般提及；
- 删除：从分析层删除整个 JD。

### 原始数据保护

所有修改只作用于：

- `zhitu_governed_job`
- `zhitu_governed_job_skill`

原始 `dataset_job_raw` 不 UPDATE、不 DELETE。

“删除整个 JD”实际为治理分析层软删除：该 JD 不再进入探新、验证、演化和图谱统计，但原始证据永久保留。

## 4. 数据库兼容升级

后端启动后会通过 `ensureSchema()` 自动补充：

- `zhitu_governed_job.is_deleted`
- `zhitu_governed_job.manual_modified`
- `zhitu_governed_job.manual_modified_at`
- `zhitu_governed_job.deleted_at`
- `zhitu_governed_job_skill.origin_type`
- `zhitu_manual_edit_log`

不会清空现有治理结果，也不会让已治理的几十万/上百万 JD 重新从零开始。

## 5. 建议升级顺序

1. 如果百万治理正在 RUNNING，先点击“安全暂停”；
2. 停止 Spring Boot 和前端；
3. 备份当前工程；
4. 覆盖 V6 补丁；
5. 重启后端；
6. 确认 `/parsing` 中已治理数量保持原值；
7. 继续从断点治理；
8. 前端执行 `npm run type-check` 后再 `npm run dev`。
